# Supported features and devices

This matrix separates implemented software from physical qualification. The [aggregate hardware evidence](hardware-compatibility.md) records the verified STU-540 firmware 1.8 workflows without retaining personal run reports. Other model profiles describe protocol targets; they are not certifications.

## Implemented

STU-540 observations include HID display/plaintext capture, stored-image restoration after a USB power cycle, background reapplication, and an initial USB COM connection with stored recall. Broader encrypted, serial, ROM and reconnect qualification remains outstanding.

`modelProfiles` are fallback format/encryption descriptions, not declarations of hardware certification. `support(reportId)` reports descriptor evidence only: HID descriptors or the serial report-size collection, restricted by the public direction catalogue. The device's active transport and firmware decide what can actually be used.

## Public report inventory

`stusign/protocol` exports all **57** public report IDs. Fifty-three entries have an implemented payload layout or a protocol-specific handler, including serial GetReport (`0x80`), SetResult (`0x81`) and ReportSizeCollection (`0xff`). Four remain explicitly `layout: 'unverified'` in `reportDefinitions`:

| ID     | Name                | Outstanding work                                  |
| ------ | ------------------- | ------------------------------------------------- |
| `0x90` | PinPadData          | Older PIN packet layout and relation to EventData |
| `0x91` | PinPadDataEncrypted | Older encrypted PIN packet layout                 |
| `0x92` | PinOperationMode    | Legacy mode payload/semantics                     |
| `0x95` | RomImageOccupancy   | Exact selector and occupancy payload              |

An inventory entry is not a successful no-op implementation. Unknown input reports emit metadata-only diagnostics. Low-level raw reads/writes do not establish a verified schema for these reports.

Separate from these four public layouts, the STU-540 firmware 1.8 descriptor contains **37 additional feature-report IDs**. [Research into every additional ID](stu-540-extra-reports-research.md) found 15 candidate firmware-loader mappings and 22 unresolved meanings. None is qualified for use on this tablet or added to the public API. The same recording contains an additional uncatalogued input report, `0xb1` (39 payload bytes).

## Limitations

STU-541 TLS, native/Node hardware transports and USB bulk I/O are not included. Older encrypted tablets require an application-supplied, reviewed `LegacyDhBackend`; the package provides the protocol adapter, not the arithmetic backend. Undocumented firmware reports are unsupported.

Encryption, autonomous modes, ROM provisioning and non-STU-540 model profiles need further physical qualification. Serial framing tests and a successful connection do not establish every serial capture or display workflow. The tables above describe the scope of the available evidence; `support()` cannot substitute for device testing.

Use the [STU-540 hardware procedure](stu-540-hardware-test.md) and [COM-mode checks](web-serial.md#physical-stu-540-checks-still-to-run) to validate the features your application uses on its actual model, firmware, browser and OS.
